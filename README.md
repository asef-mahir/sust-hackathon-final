## 1. Project Overview

**Liquidity Sentinel** is a decision-support prototype for multi-provider Mobile Financial Services (MFS) super agents operating in Bangladesh. A super agent serves customers across multiple providers — bKash, Nagad, and DBBL Rocket — from one physical cash drawer but three logically separate electronic balances.

The core problem: an agent may appear financially healthy in aggregate while one specific provider balance or the shared physical cash reserve is critically low. This gap causes service disruptions before anyone notices.

Liquidity Sentinel provides:

- A **unified real-time view** of physical cash and per-provider e-money balances
- **Forward-looking liquidity pressure signals** showing which provider or shared cash may run out, and approximately when
- **Anomaly detection** flagging unusual transaction behavior with structured evidence and calibrated confidence
- **Trilingual explanations** (English, Bengali, Banglish) generated by GPT-5 so field agents and area managers can understand alerts in their preferred language
- A **case management workflow** covering alert routing, ownership, escalation, resolution, and a full audit trail
- An **engineering evidence page** surfacing real system metrics for analytical validation

## 2. Problem Statement

> *"An agent may have enough total value but still be unable to serve customers because one provider balance or the shared cash reserve is running low."*

### The scenario

Imagine a busy market agent shop the afternoon before Eid. The shop serves bKash, Nagad, and Rocket customers from a single cash drawer but maintains three completely separate e-money ledgers. Cash-out requests surge. The agent sees each provider balance in isolation. They cannot answer a critical question: **will the shop have enough cash and provider balance to keep serving customers for the next few hours?**

The problem compounds:

- Most pressure comes from one provider — but the aggregate view looks fine
- Several transactions have nearly identical amounts from a small set of accounts — this might be normal Eid demand, a data quality issue, or something that needs review
- The agent, field officer, and provider operations team may not know who should act first or how to track the case to closure

### Data Flow — Alert Creation

```
User triggers simulation
        │
        ▼
simulationEngine.runSimulationScenario()
  → Injects synthetic transactions (atomic Prisma transaction)
  → Updates provider balances and physical cash
        │
        ▼
anomalyRules.evaluateAgentAnomalies()
  → Runs 6 rules in parallel (Promise.all)
  → Returns highest-priority finding
        │
        ▼
Alert deduplication check
  ├─ Open alert exists? → Refresh evidence + regenerate AI explanation
  ├─ Recently closed (10-min cooldown)? → Suppress
  └─ No existing alert → Create new alert
        │
        ▼
openaiClient.generateAlertAdvisory()
  → zodResponseFormat structured output (schema-enforced JSON)
  → Retry once on transient failure
  → Deterministic rule-based fallback if AI unavailable
        │
        ▼
Alert stored with explanations: { en, bn, banglish }
Agent riskStatus updated: SAFE / WARNING / CRITICAL
SimulationRun logged with duration and alert counts
```

### Alert Coordination Flow

```
Alert Created (PENDING)
        │
        ▼
OPS reviews → ACKNOWLEDGE
        │
        ├──► Mark IN_PROGRESS (OPS owns and works the case)
        │         │
        │         ├──► RESOLVE (with mandatory case note) → RESOLVED ✓
        │         └──► ESCALATE (assign to RISK owner) → IN_PROGRESS (RISK)
        │                   │
        │                   └──► RESOLVE (RISK closes) → RESOLVED ✓
        │
        └──► DISMISS (with mandatory note) → DISMISSED ✓

Every transition writes an AlertEvent (actor, timestamp, from/to status, note).
RESOLVED and DISMISSED are terminal states.
```

### Provider Separation

Each MFS provider (bKash, Nagad, DBBL Rocket) is a logically independent entity with its own `ProviderBalance` rows. The system never aggregates balances across providers for decision logic. Provider-specific alerts are scoped to their provider. The simulation engine targets one provider at a time. No feature in the application implies or enables conversion or settlement between providers.

## 12. Simulation Engine — Data and Synthetic Scenarios

### Data design principles

All data in this prototype is **fully synthetic**. No real customer identities, transaction amounts, account numbers, or provider data are used at any point. The simulation was designed to produce realistic-looking MFS agent transaction patterns for a Bangladeshi market context.

**Historical baseline** (seeded): 2,400 transactions across 4 agents over a 48-hour period, with:
- Transaction type probabilities weighted by area profile (CASH_IN_DOMINANT areas have 75% cash-in transactions)
- Random amounts between 500–50,000 BDT drawn from a seeded LCG RNG for reproducibility
- A realistic balance-updating mechanism that reflects cash-in and cash-out effects on both physical cash and provider e-money

**Synthetic account identifiers**: Transaction records contain `syntheticAccountId` values (e.g. `CUST-SIM-999`, `CUST-SIM-888`) representing simulated customers. These are placeholders with no relation to real accounts.

### The six injectable scenarios

Each scenario is triggered via `POST /api/simulation/run` with a `scenarioType`.

| Scenario | What is injected | What it tests |
|----------|-----------------|---------------|
| `HIDDEN_SHORTAGE` | 4 CASH_IN transactions (8,000–15,000 BDT each) targeting one provider, rapidly depleting its e-money balance | Detection of provider-level shortage hidden by healthy aggregate total |
| `PHYSICAL_CASH_EXHAUSTION` | 4 large CASH_OUT transactions (15,000–25,000 BDT each) draining the physical cash drawer | Detection of shared cash depletion with burn-rate projection |
| `HIGH_VELOCITY` | 6+ clustered CASH_OUTs (~5,000 BDT each) from 2 repeating synthetic account IDs in 15 minutes | Detection of suspicious velocity and amount clustering |
| `DATA_INCONSISTENCY` | 3 transactions with `isLate=true` and `isConflicting=true` flags | Degraded confidence when provider data feeds are unreliable |
| `COORDINATED_CLOSURE` | 2 CASH_OUT transactions of 150,000 BDT each across multiple providers | Detection of rapid multi-provider depletion |
| `NEGATIVE_BALANCE` | One extreme CASH_IN of 9,999,999 BDT pushing the balance into negative territory | Hard detection of impossible balance states |

### Reproducibility

Every simulation run accepts an optional `seed` integer parameter. The simulation engine uses a seeded Linear Congruential Generator (LCG) for all random values. Supplying the same `seed`, `agentId`, `targetProviderId`, and `scenarioType` will always produce the same synthetic transactions, enabling reproducible testing and validation.

### Area profile mismatch detection

The simulation engine supports a `forceProfileMismatch` flag that redirects a scenario to an agent in a contextually inconsistent area (e.g., running PHYSICAL_CASH_EXHAUSTION on a CASH_IN_DOMINANT area). This proves the rule engine detects geographic anomalies — a physical cash shortage in a CASH_IN_DOMINANT area is treated as HIGH confidence rather than LOW, because heavy cash outflow is contextually unusual for that area.

### Assumptions and limitations

- Amounts are representative approximations for a Bangladesh informal market, not validated against real MFS volume data
- Transaction timing distributions are uniform within scenario windows; real data would show time-of-day peaks
- The 4-hour survival window projection in `hiddenShortageRule` uses a linear burn-rate model; real demand is non-linear
- Area profile (CASH_IN_DOMINANT / CASH_OUT_DOMINANT / BALANCED) is a static classification computed from historical transaction ratios; it does not adapt in real time

## 13. Anomaly Detection — Rules Engine

Six rules run in parallel (`Promise.all`) for every simulation trigger. Only the highest-priority finding is surfaced per evaluation run.

### Rule 1 — Negative Balance

**Trigger**: Any `ProviderBalance.balance < 0`  
**Confidence**: Always HIGH  
**Why it matters**: An impossible state indicating a race condition, system error, or data corruption  
**Priority**: 1 (highest)

### Rule 2 — Data Inconsistency

**Trigger**: 2+ transactions with `isLate=true` or `isConflicting=true` in the last 15 minutes  
**Confidence**: Always HIGH  
**Why it matters**: Alerts operators that provider data feeds are unreliable; downstream conclusions should not be trusted  
**Priority**: 2

### Rule 3 — Coordinated Closure

**Trigger**: 2+ provider balances below 100 BDT AND 2+ CASH_OUT transactions over 10,000 BDT in the last 30 minutes  
**Confidence**: Always HIGH  
**Why it matters**: Multi-provider simultaneous depletion pattern — distinct from normal demand  
**Priority**: 3

### Rule 4 — Physical Cash Exhaustion

**Trigger**: Physical cash < 5,000 BDT AND current 2-hour burn rate extrapolates to exhaustion before cash is replenished  
**Confidence**: **Area-adjusted**  
- CASH_IN_DOMINANT area → HIGH (cash outflow is unexpected, likely urgent)  
- BALANCED area → MEDIUM  
- CASH_OUT_DOMINANT area → LOW (expected pattern; less urgent)  
**Why it matters**: Physical cash is shared across all providers; exhaustion blocks all service simultaneously  
**Priority**: 4

### Rule 5 — Hidden Shortage

**Trigger**: Any provider holds < 10% of the agent's total liquidity (physical + all provider balances)  
**Confidence**: **Area-adjusted**  
- CASH_OUT_DOMINANT area → HIGH (unexpected that digital balance is depleted)  
- Others → MEDIUM or LOW  
**Evidence provided**: `hourlyBurnRate`, `projectedDepletionMinutes`, `requiredTopUp` for a 4-hour service window  
**Why it matters**: The agent looks healthy in aggregate but cannot serve customers of the depleted provider  
**Priority**: 5

### Rule 6 — High Velocity

**Trigger**: 5+ transactions on one provider in the last 15 minutes, AND amounts cluster within 8% of their mean, AND the per-minute rate is 3x+ the 24-hour hourly baseline  
**Confidence**: HIGH if amount clustering is detected (repeated-amount pattern); MEDIUM if only velocity is elevated  
**Why it matters**: Detects both normal demand spikes (high velocity, varied amounts) and patterns requiring review (high velocity + clustered amounts from few accounts)  
**Priority**: 6

### Confidence calibration and false positives

The rules engine is designed to acknowledge uncertainty rather than hide it:

- `DATA_INCONSISTENCY` always reduces confidence in the data itself, not just the alert
- Confidence is explicitly downgraded in expected-behavior contexts (e.g., low-cash warnings in CASH_OUT_DOMINANT areas receive LOW confidence)
- The `confidenceReason` field on every alert explains in plain text why the confidence was assigned
- The `PHYSICAL_CASH_EXHAUSTION` scenario on a CASH_OUT_DOMINANT area is intentionally lower confidence because the pattern is expected — this is a deliberate false-positive mitigation

**Expected false positives**: Eid, salary day, or festival demand spikes may trigger HIGH_VELOCITY or HIDDEN_SHORTAGE alerts at MEDIUM confidence even without unusual behavior. These are surfaced as "requires review" rather than "confirmed anomaly."

## 14. AI Advisory Module

### Design

Every alert generated by the rule engine is enhanced with a trilingual explanation produced by **GPT-5 using OpenAI Structured Outputs**. The explanation is scoped to three fields:

- `reason` — one simple sentence explaining the situation (≤25 words)
- `evidence` — the exact number or time involved (≤20 words)
- `nextStep` — a safe, polite operational recommendation (≤15 words)

Each alert stores these in three languages: **English** (`en`), **Bengali script** (`bn`), and **Banglish** (`banglish` — Bengali written in Latin script).

### Why Structured Outputs

The module uses `chat.completions.parse()` with `zodResponseFormat` (OpenAI Structured Outputs), which enforces the response schema server-side at the API level. This is more reliable than `json_object` mode + post-hoc parsing because:

- Malformed or missing fields are caught before the response is returned
- Schema validation errors cannot happen after a successful API call
- `message.refusal` is checked explicitly and surfaced as a clear error

### Prompt safeguards

The system prompt instructs GPT-5 to:

- Never use words like "fraudulent", "fraud", "guilty", or "suspicious"
- Never suggest moving funds between providers
- Incorporate area profile context when it makes the alert contextually unusual
- Use natural, everyday spoken Bengali rather than literal word-for-word translation
- Never infer the time of day — the application inserts exact timestamps separately

### Fallback strategy

When GPT-5 is unavailable (no API key, timeout, refusal, or network error), the module falls back to `buildFallbackAdvisory()` — a fully deterministic local function that generates a rule-based explanation without any randomness. The fallback runs with no latency and guarantees every alert always has a usable explanation.

All alerts record `source`: `RULE_BASED` (no AI) or `HYBRID` (AI explanation attached).

### Retry behavior

- Maximum 2 attempts per alert
- 300ms delay between attempts
- Timeout per attempt: 6 seconds
- After 2 failures → immediate fallback, no further retry

## 15. Alert Coordination and Case Workflow

### State machine

```
PENDING → ACKNOWLEDGE    → ACKNOWLEDGED
PENDING → DISMISS        → DISMISSED ✓

ACKNOWLEDGED → START_PROGRESS → IN_PROGRESS
ACKNOWLEDGED → ESCALATE       → IN_PROGRESS (new owner assigned)
ACKNOWLEDGED → DISMISS        → DISMISSED ✓

IN_PROGRESS → ESCALATE → IN_PROGRESS (re-escalation to different owner)
IN_PROGRESS → RESOLVE  → RESOLVED ✓
IN_PROGRESS → DISMISS  → DISMISSED ✓
```

`RESOLVED` and `DISMISSED` are terminal states with no exits.

### Constraints enforced

- `RESOLVE` and `DISMISS` require a non-empty `note` — operators cannot close a case silently
- `ESCALATE` requires `escalateToOwnerId` — reassignment is always explicit
- All transitions are atomic: the alert update and `AlertEvent` insertion happen in a single Prisma transaction

### Audit trail

Every transition writes an `AlertEvent` record:

```json
{
  "alertId": "...",
  "fromStatus": "PENDING",
  "toStatus": "ACKNOWLEDGED",
  "actorId": "rahat-ahmed-uid",
  "note": null,
  "timestamp": "2026-07-12T09:43:11Z"
}
```

This creates a complete, immutable audit trail visible in the Alert Details timeline. The timeline shows every action taken on a case from creation to closure.

### Alert deduplication

If the same anomaly type fires again while an existing open alert exists for that agent and provider:

1. The existing alert's `evidence` and AI explanation are **refreshed** with the latest telemetry data
2. An `AlertEvent` is recorded noting the evidence refresh
3. `createdAt` is bumped so the card rises to the top of the queue
4. No duplicate alert is created

If an alert was resolved or dismissed in the last 10 minutes (cooldown window), a new alert for the same scenario on the same agent and provider is suppressed to prevent oscillation at rule thresholds.

## 17. Responsible Design Note

### Privacy

- All data is fully synthetic. No real customer identities, phone numbers, NID numbers, or account details are used anywhere in the system.
- `syntheticAccountId` values (e.g. `CUST-SIM-999`) are placeholders that carry no real-world meaning.
- Authentication uses Supabase's managed auth infrastructure. No credentials are stored in application code or logs.
- The `/api/settings/reset-demo-data` endpoint completely wipes all generated transaction and alert data on demand.

### Human review boundary

Liquidity Sentinel is explicitly a **decision-support tool**, not a decision-making tool. The system:

- **Never automatically blocks** an agent, freezes a balance, or initiates any financial action
- **Never declares fraud** — the language "requires review" and "unusual" is enforced in the AI system prompt at a model level, not just as a UI disclaimer
- **Never makes a final determination** — every high-confidence alert ends with a human `RESOLVE` or `DISMISS` action that requires an explicit case note
- **Always escalates to a human** — the `ESCALATE` action reassigns ownership to a named person (e.g. the RISK analyst) rather than triggering automated action

### False-positive acknowledgment

The system is explicitly designed to acknowledge its own uncertainty:

- `DATA_INCONSISTENCY` findings reduce confidence in all downstream conclusions, not just in the inconsistency itself
- Area profile context is used to downgrade confidence for expected-behavior patterns (CASH_OUT_DOMINANT areas are expected to have frequent cash depletion)
- The `LOW` confidence level is a first-class value — it is surfaced to operators, not hidden
- Eid or salary-day scenarios may trigger alerts at MEDIUM confidence; the AI explanation includes "this may be normal seasonal demand" as part of the context

### Provider separation

- Provider balances are stored and displayed per provider, with no cross-provider aggregation used in any alert logic
- No feature implies, enables, or suggests conversion, settlement, or transfer between providers
- The simulation engine targets exactly one provider per run; it never touches another provider's balance as a side effect
- The AI system prompt explicitly instructs the model: "Never suggest moving or converting funds between different providers"

### Actions the prototype intentionally does not perform

| What it does not do | Why |
|---------------------|-----|
| Execute real financial transactions | Out of scope; would require regulatory authorization |
| Access real bKash, Nagad, or Rocket APIs | Not authorized; uses simulation only |
| Accuse agents of fraud | Unacceptable without real evidence, human review, and legal authority |
| Automatically freeze accounts or balances | No automated enforcement mechanism exists |
| Collect PINs, OTPs, or authentication credentials | Never prompted or stored anywhere in the system |
| Claim production fraud-detection readiness | The system is explicitly a prototype for research and demonstration |

## 19. Known Limitations and Next Steps

### Current limitations

| Area | Limitation |
|------|-----------|
| **Liquidity forecast** | Uses a linear burn-rate model. Real demand is non-linear with intraday peaks. A time-series model (ARIMA, LSTM) would improve forecast accuracy. |
| **Area profiles** | Static classification recalculated manually via `npm run update-profiles`. A production system would recalculate continuously in the background. |
| **Anomaly rules** | All 6 rules use fixed thresholds (e.g., < 10% for hidden shortage, 5+ transactions for velocity). Adaptive thresholds learned per-agent would reduce false positives. |
| **In-memory metrics** | The AI call tracker (`lib/metrics.js`) resets on server restart. A persistent metrics store (e.g., time-series DB) would be needed for production monitoring. |
| **Single finding per evaluation** | The rule engine surfaces only the highest-priority finding per simulation run. In production, all concurrent findings should be surfaced independently. |
| **No realtime push** | Alert updates require page refresh or polling. WebSocket or Supabase Realtime subscriptions would enable live dashboard updates. |
| **Agent self-service** | The AGENT role view is read-only. A production system would allow agents to request liquidity support through the application. |
| **ML forecasting** | The `/analytics` page has a `ForecastingEmptyState` placeholder. Actual ML-based depletion forecasting is not yet implemented. |

### Next steps for a production system

1. **Adaptive anomaly thresholds** — Learn per-agent baseline behavior over rolling windows and adjust rule thresholds automatically
2. **Time-series forecasting** — Integrate ARIMA or Prophet for intraday liquidity projection with confidence intervals
3. **Supabase Realtime** — Push alert state changes to connected dashboards without polling
4. **Agent mobile interface** — A lightweight mobile view (PWA or React Native) for the agent role
5. **Provider API integration** — Replace simulation with actual (authorized) provider feed adapters
6. **Audit export** — CSV or PDF export of alert timelines for compliance documentation
7. **Multi-language UI** — Extend the Banglish/Bengali language preference to the full interface, not only alert explanations
8. **Load testing** — Validate behavior under realistic agent network scale (100+ agents, 10,000+ daily transactions)
